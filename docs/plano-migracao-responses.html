Chat Completions + Responses API

Faz sentido oferecer suporte aos dois protocolos. O trabalho principal não é trocar a URL: é adicionar um adaptador Responses ao lado do Chat atual, com seleção explícita por provider, sem quebrar o contrato existente do Harness e dos gateways.

Resposta curta: sim — suportar ambos é a melhor escolha. A OpenAI ainda suporta Chat Completions e recomenda Responses para projetos novos. Mantenha os dois adaptadores disponíveis e escolha explicitamente o protocolo por provider (e, se necessário, por modelo). Chat Completions continua sendo o padrão de compatibilidade para configurações existentes; Responses fica disponível onde foi validado.
Ressalva essencial: ainda não está provado que todos os endpoints configuráveis no BH aceitam POST /v1/responses. Em particular, não presumir que o default OpenCode Zen expõe a mesma rota só porque o upstream OpenAI a tem. O catálogo /models também não atesta suporte a Responses.

1. O que o BH faz hoje

O limite do protocolo está bem concentrado: internal/dealer/dealer.go serializa o transcript interno em Chat Completions, envia /chat/completions e interpreta o SSE. O runtime já mantém uma representação própria (dealer.Mensagem) com mensagens de usuário/assistente, tool call/result e imagens — isso evita reescrever toda a orquestração do agente.

Boa notícia: o dealer já é a fronteira adequada para a tradução. A intenção é preservar runtime, executor de tools, persistência e CLI, adicionando um adaptador Responses ao lado do atual.

2. O formato Responses que o dealer precisa falar

Request

Exemplo conceitual para uma chamada de streaming com tool local. Em produção, o BH enviaria todos os itens do transcript que decidiu conservar:

POST /v1/responses
{
  "model": "model-id",
  "instructions": "instruções estáveis do BH e BARROSO.md",
  "input": [{ "role": "user", "content": [
    { "type": "input_text", "text": "Leia o arquivo e explique." }
  ]}],
  "tools": [{
    "type": "function",
    "name": "read",
    "description": "...",
    "parameters": { "type": "object", "properties": { "path": { "type": "string" } }, "required": ["path"] }
  }],
  "tool_choice": "auto",
  "reasoning": { "effort": "medium" },
  "max_output_tokens": 32768,
  "store": false,
  "include": ["reasoning.encrypted_content"],
  "stream": true
}

Instruções de sistema podem ir no campo instructions ou como item system/developer de input. Se usar previous_response_id, a documentação alerta que as instruções de topo não são herdadas: precisam ser reenviadas a cada request.

Conversão do transcript e multimodalidade

  • Texto do usuário vira item input_text; imagens viram input_image com URL ou data URL. O código atual já lê e inline imagens, mas muda o envelope.
  • Texto do assistant que é reproduzido no histórico usa output_text; chamadas locais viram {type:function_call, call_id, name, arguments}.
  • Resultado de tool vira {type:function_call_output, call_id, output}. Use o call_id da chamada — não confunda com o id do item Responses.
  • Responses aceita ferramentas function planas, diferente do formato nested atual. Não forçar strict:true sem antes normalizar e testar os schemas do catálogo dinâmico do BH.
  • max_output_tokens conta tokens de raciocínio e de resposta; confirmar que o teto do BH e sua regra de retry/corte produzem o limite desejado.

Stream tipado, não Chat chunks

response.created                         → metadata e começo da rodada
response.output_text.delta               → acrescentar texto
response.function_call_arguments.delta   → acumular argumentos por item_id/output_index
response.output_item.done                → fechar item; função recebe call_id/name/arguments finais
response.completed                       → resposta terminou; ler usage
response.incomplete                       → terminou incompleta; mapear incomplete_details
response.failed / error                  → falha do provider, nunca resposta vazia bem-sucedida

O parser deve aceitar eventos desconhecidos sem travar em extensões futuras, mas reconhecer erros e terminais. Não assumir que [DONE] sozinho é o término semântico: Responses tem eventos de ciclo de vida. Usar response.output_item.done para finalizar tool calls evita executar argumentos parciais.

3. O que o código do OpenCode ensina

Há implementação funcional de Responses no repositório OpenCode. A parte mais útil para o BH é o adaptador de provider em packages/core/src/github-copilot/responses/. Ele mostra que a migração é uma adaptação de ponta a ponta, não uma troca de endpoint.

openai-responses-language-model.tsConstrói request; usa max_output_tokens, reasoning.effort, store/include; envia para /responses; tem handlers JSON e SSE e interpreta usage/itens.

openai-responses-api-types.ts e map-openai-responses-finish-reason.tsTipos discriminados dos items e conversão de término para stop/length/tool-calls.

Outro adaptador no código de protocolo do OpenCode, packages/llm/src/protocols/openai-responses.ts, ilustra a redução de mensagens internas para items, parser SSE por evento, stream de funções e metadados de reasoning. Ele também mostra que raciocínio e texto são itens separados e que as chamadas de tools hospedadas pelo provider pedem tratamento próprio.

Não portar o OpenCode inteiro: reaproveitar os formatos e os casos de teste, mas manter o dealer e o modelo interno do BH. O OpenCode usa abstrações/SDKs e cobre tools hospedadas além do conjunto local do BH.

4. Estado de conversa, raciocínio e gateways

Histórico gerenciado pelo BH — recomendado no primeiro passo

Enviar a cada request os itens do transcript atual, como já faz a harness; usar store:false explicitamente e não depender de IDs remotos. Isso mantém compactação, pruning, /new e /resume sob controle local.

Atenção: reasoning models podem exigir replay dos output items completos, inclusive reasoning.encrypted_content e mensagens/calls, para preservar contexto entre requests stateless. O transcript atual do BH não persiste esses metadados; desenhar sua serialização antes de declarar o raciocínio entre rodadas equivalente ao Chat.

previous_response_id — não habilitar por padrão

É uma opção útil da API quando se quer contexto armazenado/remoto. Porém o BH compacta/edita o histórico, recupera sessões de SQLite e pode fazer retries com corpo diferente; uma cadeia remota oculta pode reintroduzir contexto removido ou duplicar o transcript enviado.

Se for adotado depois, persistir response IDs por conversa, invalidar a cadeia ao compactar, resetar ou trocar provider/modelo, reenviar instructions e validar privacidade/retenção do endpoint.

Compatibilidade depende da URL. O gateway Barroso Keys tem uma rota Responses documentada/implementada, mas ela traduz para Chat Completions no roteador comum; não é prova de que a geração foi nativa Responses. O gateway não armazena responses e recusa previous_response_id, conversation, background e templates prompt. Outros endpoints (inclusive Zen e proxies OpenAI-compatible) precisam de probes próprios.

Para usage, mapear input_tokens → prompt, output_tokens → output, input_tokens_details.cached_tokens → cache e output_tokens_details.reasoning_tokens → tokens de reasoning. Mapear incomplete_details.reason == max_output_tokens para a rotina de corte atual; status failed deve retornar erro, não uma rodada sem conteúdo.

5. Plano de implementação do suporte duplo

0

Fechar o contrato por endpoint

Fazer smoke probes sem credenciais em logs e sem alterar o default: cada provider deve confirmar rota, autenticação, SSE Responses, tools, imagens, reasoning/effort, usage e limites de parâmetros. Separar explicitamente o que é OpenAI nativo, Barroso Keys (tradução) e OpenCode Zen. Não inferir capacidade por /models.

1

Introduzir escolha explícita Chat/Responses

Adicionar configuração persistida ao provider (por exemplo protocol: chat_completions | responses), mantendo chat_completions para configs existentes. Expor a escolha no fluxo de /provider e passá-la a dealer.Config. Se modelos diferentes no mesmo endpoint tiverem capacidades distintas, permitir uma sobrescrita por modelo. Não tentar automaticamente o outro protocolo depois de um erro: isso pode duplicar custo, ocultar incompatibilidade ou repetir uma rodada com tools.

2

Adicionar serializador Responses

Manter Corpo/CorpoEstimativa para Chat; criar par equivalente para Responses. Traduzir system, histórico, ferramentas, tool_choice, imagens, effort e output cap. Adaptar normalização da URL para não duplicar /responses. A estimativa de contexto precisa usar o mesmo formato/itens reais (com imagem stand-in), ou orçamento e request divergirão.

3

Implementar parser SSE tipado

Criar parser por type: texto, reasoning summary se habilitado, output item iniciado/finalizado, deltas e conclusão de argumentos, usage, incomplete, failed e error. Correlacionar tool calls por item_id/output_index; executar só depois do item completo. Preservar a lógica já existente de watchdog, cancelamento, HTTP errors e retries.

4

Decidir como replayar reasoning e persistir metadados

Escolher e documentar política antes do rollout: guardar os output items Responses necessários no transcript/log (incluindo encrypted reasoning) para replay manual, ou provar outro mecanismo compatível com compactação/resume. Se o log só guardar texto e argumentos, a sessão aparentemente funciona, mas pode perder contexto de reasoning nas próximas rodadas. Começar com store explícito e política de privacidade consciente.

5

Revalidar o wire contract do OpenCode Zen

O caminho atual usa tool_choice:auto, headers de sessão/User-Agent e tool definitions byte-exactas/fingerprintadas. Responses tem schema diferente e pode seguir gate diferente. Testar primeiro sem alterar o contrato Chat; validar também o efeito dos decoys/fingerprint read/shell e a recepção dos headers na rota Responses. Não adicionar os tools Chat-format à requisição Responses.

6

Rollout gradual do protocolo escolhido

Habilitar Responses apenas em provider/modelo comprovado, mantendo Chat Completions plenamente suportado. Medir TTFT, duração, cache hit, input/output/reasoning tokens, falhas e uso de tools; comparar tarefas equivalentes nos dois protocolos. Atualizar README, onboarding/config e fixtures. Não é necessário remover Chat nem torná-lo indisponível para adotar Responses em endpoints que o suportam.

6. Critérios de aceite antes de trocar o default

Contrato de request

  • Rota e auth corretas; sem /v1/v1 nem /responses/responses.
  • Instruções estáveis; schema e escolha de tools válidos.
  • Estimativa de contexto alinhada ao body real com imagens.

Agente e transcript

  • Uma tool e chamadas paralelas; argumentos fragmentados não executam antes do final.
  • Results associados ao call_id certo e tool loop segue até resposta final.
  • Pruning/compaction, interrupção, retry e /resume sem chamadas órfãs nem contexto duplicado.

Terminal, usage e segurança

  • Completed, incomplete por limite, failed, error e stream interrompido diferenciados.
  • Tokens/cache/reasoning e tempos chegam ao rodapé/telemetria existentes.
  • Política de store explícita; key nunca entra em log/HTML/tests.

Testes: criar fixtures determinísticas SSE Responses no dealer; testar o body e parser por unidade; servidor httptest para rota/headers/eventos; usar fakes de runtime para tool loop e recuperação. Preservar a suíte Chat e adicionar smoke manual por endpoint em chave/modelo autorizado. Um HTTP 200 de texto simples não basta: a chamada de tool, a resposta correspondente e a segunda chamada do modelo também precisam passar.
